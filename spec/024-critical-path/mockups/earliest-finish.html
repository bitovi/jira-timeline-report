Epics on the critical path

Mockup for the capacity-blind report described in spec/024-critical-path/dependency-floor.md. Deliberately isolated from critical-paths.html, which mocks the capacity-aware report. Sample data below is internally consistent: every percentage and every day figure reconciles, so the arithmetic can be checked by hand.

1 · What the report answers

One question, asked by a program manager: which epics should I look at first? The answer is ranked by how many days each epic adds to the longest chain of Blocks links, measured on sampled durations and recomputed every simulation run. Team contention is ignored entirely, so this is about the shape of the plan rather than its staffing.

It is not “the plan with unlimited people.” A team's throughput is fixed by velocity; parallelWorkLimit only divides that throughput into lanes. Hiring lowers this number, adding a track raises it. The number holds each epic's duration as configured and removes only the queueing.

2 · The two numbers, and what to call them

Every row carries the same two quantities. Only the labels are in question.

  • Quantity A — the share of simulation runs in which this epic was part of the longest chain. Sample value: 68%.
  • Quantity B — A multiplied by the epic's average duration on those runs. Sample value: 7.8 d. Across all epics, B sums to exactly the critical path length.

4 · Why rank by days rather than by percentage

Both orderings, same data. The disagreement is the point.

Ranked by days chosen
Payments API 11.8 41%
Checkout rewrite 7.8 68%
Identity service 7.3 68%
Search indexing 6.0 26%

Payments first: on the chain only 41% of the time, but it is a 29-day epic.

Ranked by percentage rejected
Checkout rewrite 7.8 68%
Identity service 7.3 68%
Payments API 11.8 41%
Search indexing 6.0 26%

Percentage is blind to size. Checkout is an 11-day epic; trimming it cannot pay what trimming a 29-day one pays. Taken to its limit this ranking puts a 2-day epic that is always on the chain at the top.

The percentage still earns its column: it separates Search indexing (23 d, rarely on the critical path) from Checkout (11 d, usually on it). Same rough payoff, completely different reasons, and different fixes.

Conventional and safe. Adds scannability when the list is long, adds nothing when it is short. Since the list is already sorted descending, the bar is redundant with row order — it only conveys the gaps between values, e.g. that Payments is far ahead of the pack.

5b · One segmented bar of the whole 43 rejected

Segments sum to exactly 43 d, because the decomposition is exact.

Do not build this. It sits directly beneath an actual Gantt chart, so a horizontal bar segmented left-to-right reads as a timeline. It is not one. The segments are expected values averaged across different runs; those epics never run back-to-back in that order in any single run, and several are on different chains entirely.

The exactness is real, but it does not license this encoding.

5c · No bars viable

Eight rows of two short numbers. Sorted. The table may simply not need a chart, and the surrounding Auto-Scheduler page is already dense.

6 · What clicking a row does

  • Highlights that epic in the Auto-Scheduler grid above, reusing the existing highlight wiring.
  • Dims routes in the right-hand card that do not contain it — showing at a glance whether the epic is a junction (on many routes) or the tail of a single one.

7 · Decisions taken

  • Rank epics, not chains. Chains fragment across forks and hide junction epics.
  • Rank by days, not by percentage. Percentage is size-blind.
  • Routes list is context, capped at five, safely truncatable.
  • No second series. Queued time is zero by construction in this report, so there is no work/wait split.
  • The table is the product, not the total. The three-stat headline strip is gone: a program manager acts on which epics to look at, and the 43 d is only useful as the column total. It sits in the table footer.
  • The contention gap (plan finish minus critical path length) moves to the capacity-aware report, where the remedy lives. Restating the plan finish here duplicated the Gantt and mixed two different statistics.
  • Averages throughout, not percentiles. The per-epic days sum to the total only for the mean.
  • No segmented total bar — reads as a timeline directly under a real one.
