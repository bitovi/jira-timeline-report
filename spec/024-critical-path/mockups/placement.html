Placing the critical-path tables

Follow-on to earliest-finish.html, which settled what the two tables show but left where they live open. critical-paths.html section 3 answered that question for the capacity-aware report and chose a controls dropdown — but that dropdown was designed around a single list of paths, and we now have two tables that need to coexist. This page re-opens the placement question with that constraint in hand.

All sample data is the real IMP-99, IMP-100 plan: 91-working-day finish, 53.8-day critical path, ORDER-Team 87 days on one track.

1 · The problem, stated precisely

Three requirements that pull against each other. Any option has to be scored on all three.

  • Discoverability. Both tables currently sit below the Gantt. In a 200-epic plan that is several screens down. People do not find them.
  • Two peer tables. The epics table ranks what to shorten. The routes table shows how likely any given chain is to be the one that matters — which is how you judge whether an intervention has leverage at all. earliest-finish.html called routes "context only"; that is wrong, and this page treats them as equals.
  • Co-visibility with the grid. Clicking an epic row highlights it in the Gantt. That interaction is pointless if the grid is off-screen when you click.

The third requirement is the one that kills most layouts. It rules out any full-page mode switch, and it means "scroll down to the tables, click, scroll back up" is a broken loop. The tables and the grid have to share a viewport.

2 · The one line that should always be visible

Independent of which option wins. earliest-finish.html section 7 moved the contention gap out of this report and into the capacity-aware one — but that report may not ship, so the number currently appears nowhere. It is the most decision-relevant figure on the page: it says whether to cut scope or add capacity.

Critical path 53.8 d of 91 d finish · 37.2 d is queueing, not dependencies · top epic Add promotion to cart 35.4 d Details ▾

Roughly 28px. Read left to right it is a complete diagnosis: the dependency floor, the actual finish, the gap between them, and the single epic most worth shortening.

Every option below assumes this bar exists. The options differ only in what happens when you expand it.

4 · Selection runs both ways

The two tables answer halves of the same question, so selection has to be symmetric. Pick an epic and you want to know which chains it sits on; pick a chain and you want to know which epics compose it. Today neither direction exists: routes are not clickable at all, and selecting an epic filters the routes list rather than highlighting within it, which throws away the comparison you selected in order to make.

The four lit epics sum to 44.2 of the route's days — 35.4 + 7.3 + 1.0 + 0.5 — so you can read straight off it that one epic owns 80% of the chain. That is the "which link do I attack" question, and it has no answer today.

The model. One selection, of one of two kinds, driving three surfaces.

  • { kind: 'epic', key } — lights the epic row, every route containing it, and the epic in the Gantt.
  • { kind: 'route', id } — lights the route row, every epic on it, and the whole chain in the Gantt.
  • null — nothing dimmed.

Clicking a lit row again clears the selection. Dim, never filter — the same call critical-paths.html option A made for the grid.

This kills the "merge the two tables" idea that an earlier draft of this page recommended. Folding routes into an expandable detail row under each epic supports epic → routes and makes route → epics impossible, because a route no longer has a row to click. Bidirectional selection requires two peer tables, side by side, both on screen at once.

5 · The combination — B with a toggle, plus a compact confidence control

B's fatal flaw was that a permanent 210px rail wrecks both tables and squeezes the Gantt. Two changes fix it. A toggle on the far right of the controls row makes the rail optional, so the Gantt is full width whenever you are not using it. And replacing the ~600px confidence slider with option D from confidence-control.html — the drag-across segmented strip, ~230px — frees the room the toggle needs to sit in the controls row at all.

Both wireframes below are live. Click Critical path to toggle the rail. Drag the divider between the grid and the rail to resize it.

The "Critical path length" footer is gone, and 5c is the current content treatment — 5a and 5b above still show the old one, because they exist to compare placement rather than content.

earliest-finish.html section 7 put the total in the table footer deliberately: "it is a total, not a headline." That was right for a full-width card with no header stat. In the rail it is wrong, because 53.8 was appearing three times in one panel — in the header, in the caption under the card title, and again in the footer. Exactly the duplication that got 91 d removed.

The header keeps it, because it is the one place that pairs it with the queueing gap and stays visible while the list scrolls. The footer is replaced by a residual row, which is strictly more informative: it says the list is truncated, and it still lets you check the arithmetic against the header.

Do not restate the plan finish in the rail. The Summary band at the top of the grid already carries it, two inches away. Repeating 91 d in the rail header buys nothing.

And restating it would be actively wrong at most slider positions. planEstimateText in AutoScheduler.tsx tracks the confidence slider: a single mean at average, a single value at median, and a planBottomDays–planTopDays range at every percentile. The critical path length does not track it at all — meanPathLength() is unconditionally the mean across iterations, because that is the only statistic for which the per-epic days sum to the total.

So at 80% confidence the Summary might read 98–112 working days while the floor is still 53.8. A “gap” computed across those is a percentile minus a mean, which is not a quantity. Either the gap is shown only at average, or it is labelled as being against the average finish regardless of the slider.

Median is not a safe third option either, which an earlier draft of this page got wrong. Two reasons. The plan's median finish and the floor's mean are different statistics, and with GSD 1.33 the distribution is right-skewed, so median < mean and the gap would be understated. And the per-epic decomposition fails outright at the median: an epic's contribution is zero on every run it is not on the path, so any epic on the path less than half the time has a median contribution of exactly 0. A median column would read 0.0 for most of the table.

5d · Vertical budget — two capped scroll regions, expandable residuals

Yes, it depends on browser height — but nothing needs measuring in JS, and the two tables do not need to negotiate for space at all.

1 · The report area is already a bounded scroll container. TimelineReport.tsx renders <div class="fullish-vh … overflow-y-auto">, and updateFullishHeightSection() writes its page offset into a CSS variable on <html>, refreshed on load and resize. There is even a utility that consumes it: .height-fullish-vh { height: calc(100vh - var(--fullish-document-top)) }.

So the rail's height budget is already computed and published. The rail caps itself with max-height: calc(100vh - var(--fullish-document-top)) and needs no ResizeObserver of its own.

2 · The rail must be position: sticky; top: 0. This is not cosmetic. The grid scrolls inside that container, so a statically positioned rail scrolls away with it — and forty epics down the Gantt the tables would be off screen, destroying the co-visibility that justified this whole layout in section 1.

Within that budget: each table is capped at a row count and scrolls inside its own cap. Epics get 10 rows, routes get 5. Neither can be starved by the other, because neither is claiming the leftovers. The residual row at the bottom of each is a button — click 6 other epics and the rest write out in place; click again to collapse.

Two earlier drafts of this section were wrong, in opposite directions.

The first gave the epics card the flex remainder and let routes keep their natural height. Measured, the fixed furniture came to ~300px, so at a 300px budget the epics list got 0px — present, scrollable, showing nothing. The panel looked broken.

The second made the whole rail one scroll region with both tables at natural height. Nothing collapsed, but the routes table could sit entirely below the fold — so selecting an epic would light routes you could not see, firing the section 4 interaction off screen.

Two capped scroll regions fixes both. Each table has an intrinsic size, so neither collapses; both are always at least partially on screen, so the bidirectional selection stays legible at any height.

  • Caps, not shares. max-height on each scroll area rather than flex: 1. Measured on the demos above — at 620px neither cap binds; at 420px the cards are 160px and 115px; at 300px they are 88px and 67px. Both stay usable throughout, and the rail itself does not scroll until about 250px — roughly a third of the 380px floor the flex version needed.
  • Epics 10, routes 5. Not inconsistent — an epic row is one line, a route row is a wrapped chain two or three lines tall. Ten routes would be ~350px against ~230px for ten epics. Five is also the cap earliest-finish.html already set.
  • The DOM stays small until asked. A 200-epic plan still renders 10 rows plus a residual. Expanding is user-initiated, so the default case needs no virtualisation.
  • Expanding beats a plain "show more". The residual already carries an aggregate — 0.7 days across 6 epics — so it is informative while collapsed and honest about what is hidden.

The cost is nested scrolling, and it is worth naming. Inside a page that already scrolls, the rail can scroll, and inside that each table can scroll. Three levels is enough to feel sticky if the wheel chains badly.

In practice it is two levels, not three: the rail only scrolls below ~250px of budget, shorter than any real window. overscroll-behavior: contain on the table scroll areas stops a flick inside the epics list from running away with the page.

One trap this uncovered, which would have shipped silently. .mini sets overflow: hidden, and that resets a flex item's automatic minimum size from min-content to zero. With no explicit min-height the cards kept shrinking past their own headers and clipped their rows rather than overflowing to the rail — the rail reported no scrollbar while content was being cut off invisibly. At a 200px budget it looked fine and was not.

The fix is explicit minimums on each card (100px epics, 80px routes), after which the rail scrolls as intended below ~250px. Worth remembering for any scrollable card inside a flex column.

Order: routes first, epics second. Swapping them was tested in the browser and changes no heights at all — both cards shrink symmetrically under the capped-scroll model, so routes-on-top does not squeeze the epics ranking the way it would have under the flex model. That leaves the decision entirely to reading order.

The panel is labelled "Critical path", so the first thing under that label should be critical paths. Leading with a table of epics makes the panel fail to deliver what its own header and spine promise — a first-glance cost, paid by every user on every open.

It also reads in the right order: "here are the chains that decide the date", then "here is which epic inside them to attack". The routes list is the calibration — how likely any chain is to be the one that matters — and the epics ranking is only worth acting on once you have it.

What this costs. The header states the dependency floor, and it is the epics column that sums to it; with routes in between, those two are no longer adjacent. The epics caption carries the tie instead — "Days each epic adds to the dependency floor" — which names the relationship without restating the number and re-introducing the duplication removed in 5c.

5e · What "dependency floor" means, and the tooltip it needs

The number is easy to state and easy to misread, so it needs help at the point of use. It is the mean, across simulation runs, of the longest chain of Blocks links weighted by that run's sampled durations, with team queueing removed.

Three misreadings to design against:

  • "This is the plan with unlimited people." It is not, and earliest-finish.html section 1 already says so: throughput is fixed by velocity, and parallelWorkLimit only divides it into lanes. Each epic still takes as long as its team's configuration says. What is removed is queueing behind other work in this plan — nothing else.
  • "We could finish in 53.8 days." It is an average, so roughly half of runs have a longer chain than that. It is a lower bound on the mean finish, not a target and not a date.
  • "The floor and the gap are separate levers." They are not cleanly separable. Shortening an epic that sits on the bottleneck team shrinks both at once — which is exactly what makes Add promotion to cart worth 35 days in this plan.

Proposed tooltip copy — on the Dependency floor label in the rail header.

Dependency floor · 53.8 working days
The average length of the longest chain of Blocks links, if no epic ever waited for a free track.

Team velocity still applies — each epic takes as long as its team's throughput allows. Only queueing behind other work in this plan is removed.

This plan averages 91 days, so 37.2 days are queueing. Lowering the floor means smaller epics or fewer dependencies. Closing the gap means capacity or sequencing.

Always an average. It does not follow the confidence slider.

The name is a risk worth noting. "Floor" correctly implies a bound you cannot get under, but it invites the second misreading above — people hear a floor as something you could stand on. "Earliest finish", the name the original mockup file carries, is worse: it promises a date and a best case, and this is neither.

Keeping Dependency floor with the tooltip is the cheapest option. If the tooltip turns out not to be enough, the honest alternative is longer and duller — Dependency-only length (average).

How hard is the draggable divider?

Easier than it looks, because the two things that usually make Gantt resizing painful are already handled.

  • The grid reflows for free. gridTemplateColumns: [what] auto repeat(N, 1fr) — the day columns are fractional and every bar is positioned in %. Narrowing the container rescales the timeline with no JS.
  • The dependency curves already redraw on resize. AutoScheduler.tsx mounts a ResizeObserver on the SVG container plus a window.resize listener, both calling updateBlockers. The SVG paths are rebuilt from live getBoundingClientRect() measurements, so a drag re-draws them with no new code. This is the part that would otherwise be days of work.
  • What you actually write is a pointer-event handler: pointerdown → setPointerCapture → pointermove writes a width to a CSS variable → pointerup persists it. Roughly the amount of code in this mockup's <script> block, which is the working implementation you are dragging right now.

The real costs are the edges, not the drag:

  • updateBlockers rebuilds every path from scratch and queries the whole document (document.querySelectorAll('.work-item')). Firing that on every pointermove will stutter on a 200-epic plan. Needs requestAnimationFrame coalescing, and possibly redrawing only on pointerup while showing a plain divider line during the drag.
  • The [what] column is auto and the name cells are truncate max-w-sm, so the grid stops shrinking once names hit their max width. The drag needs a minimum, or the name column needs to shrink with the container.
  • Persisting the width — component state, localStorage, or the saved report.
  • Keyboard accessibility: the divider needs role="separator" and arrow-key resizing.
