# Storing data in Jira projects — `STATREPS` and `TEAMMAP`

> Companion to [README.md](./README.md). Read [§2 How much storage we get](./README.md#2-how-much-storage-we-get)
> first — the case for this design rests on the three problems listed there, not on the byte count.

The premise: a saved report and a team configuration are both _records with an owner, a lifecycle,
and an audience_. Jira already has a first-class object with all three. Stop hiding them in a blob.

## The shape

Two projects, both optional, both pointed at by config rather than hardcoded:

```
STATREPS  (one issue per saved report)          TEAMMAP  (one issue per team)
├─ STATREPS-1  "Q3 Platform Status"             ├─ TEAMMAP-1  "Platform"
├─ STATREPS-2  "Exec Rollup"                    ├─ TEAMMAP-2  "Payments"
└─ STATREPS-3  "Payments Timeline"              └─ TEAMMAP-3  "Mobile"
```

`STATREPS` is a straight one-to-one with today's `saved-reports` entries. `TEAMMAP` is a one-to-one
with today's `all-team-data` keys — and the keys are already team _names_
(`getTeamKeyDefault`, `src/jira/normalized/defaults.ts:169`, which reads `fields.Team.name` and falls
back to the project key), so "one issue per team, summary = team name" needs no new identity scheme.

Neither project should be _required_. A site that never creates them keeps the app-property backend
and never notices this feature exists.

## Where the payload actually lives

This is the decision that matters most, and it is a genuine trade-off rather than a clear win.

### Option A — issue **entity property** on the report issue

`PUT /rest/api/3/issue/{key}/properties/bitovi.status-report.payload`

- **32,768 bytes per property, unlimited properties per issue.** A single report that outgrows one
  property can shard into `…payload.1`, `…payload.2` without a schema change. This is the only
  storage primitive in the whole survey with an uncapped count.
- Invisible in the Jira UI, so users can't accidentally corrupt it by editing the description — the
  exact failure the website backend is exposed to today.
- Not text, so no ADF round-tripping, no code-block scanning, no `JSON.parse` of user-editable prose.
- **But: entity property writes do not appear in issue history.** You lose the free versioning that
  is one of the three reasons to do this at all.

### Option B — payload in a ```json code block in the description

- **Free versioning** — every save is an issue history entry with author and timestamp, and Jira's
  UI already diffs descriptions.
- Debuggable by a human with no tooling.
- **But: 32,767 chars shared with any prose in that description**, and users can and will edit it.
  This is exactly the website backend's failure mode, just scoped to one report instead of all of them.

### Recommended: A as the source of truth, plus a rendered human view in the description

Write the payload to the entity property. Write a **read-never, human-only** rendering into the
description — report name, JQL, report type, a deep link back into the app, and a "generated by
Status Reports for Jira, edits here are ignored" line. The app never parses the description.

That gets robustness _and_ an audit trail (the rendered view changes when the payload does, so
history still tells you who changed what and roughly what changed), at the cost of one extra write
per save. If that write fails, the payload is still correct — the description is decoration.

Indexed fields for free, on the issue itself:

| Jira field                     | Holds                                                                       |
| ------------------------------ | --------------------------------------------------------------------------- |
| Summary                        | Report name — searchable, sortable, and it's what shows in every Jira UI    |
| Description                    | Rendered human view (never parsed)                                          |
| `bitovi.status-report.payload` | `{queryParams, sections?, schemaVersion}`                                   |
| Reporter / Created / Updated   | Author and timestamps, free                                                 |
| Labels                         | Report type (`start-due`, `cards`, `report-of-reports`) — JQL-filterable    |
| Issue key                      | Stable id. Note: **not** today's `Report.id`; see [§ Migration](#migration) |

Same layout for `TEAMMAP`, with the payload being the `TeamConfiguration` (`defaults` + per-hierarchy
overrides) and the summary being the team name.

## What this buys, concretely

**Permissions.** `STATREPS`'s permission scheme is the ACL. Browse Projects controls who sees which
reports; Create/Edit Issue controls who can save. Where a site has issue security schemes, individual
reports can be restricted. None of this is buildable on a single app-scoped blob.

**Concurrency.** Two people editing two different reports write two different issues. The
read-modify-write race in `updateReports` (`src/jira/reports/fetcher.ts:32`) stops being able to lose
an unrelated person's work. Same-report races still exist — Jira's edit API has no optimistic
concurrency — but the blast radius drops from the collection to the record.

**Headroom.** ~32 KB per report, unlimited reports, versus ~73 reports total. Effectively unbounded
for this workload.

**Everything Jira already does.** Comments, watchers, `@`-mentions, global search, linking a report
to the initiative it reports on, "show me every report touched this quarter" as a JQL query.

**Survives uninstall.** App properties are deleted when the app is removed. Issues are not. For a
customer evaluating the paid app, "your reports stay yours" is a real answer.

## Cost model

| Operation          | Today (plugin)                    | Today (website)                      | `STATREPS`                                                                 |
| ------------------ | --------------------------------- | ------------------------------------ | -------------------------------------------------------------------------- |
| List reports       | 1 property GET                    | 1 JQL search                         | 1 JQL search — **if** the search endpoint returns entity properties inline |
| Open one report    | (from the list)                   | (from the list)                      | (from the list), else 1 property GET                                       |
| Save one report    | 1 property PUT (whole collection) | 1 search + 1 edit (whole collection) | 1 property PUT + 1 description edit (**one report**)                       |
| Delete             | 1 PUT (whole collection)          | 1 search + 1 edit                    | 1 issue transition or delete                                               |
| Cold boot (4 keys) | 4 property GETs                   | **~5 JQL searches**                  | 1–2 searches + property GETs                                               |

> **The load-bearing unknown.** If `/rest/api/3/search/jql` accepts a `properties` param and returns
> entity properties inline, listing is one request and this design is strictly cheaper than the
> website backend is today. If it does not, listing is 1 + N requests and we need a different index —
> most likely a **project property** on `STATREPS` holding a compact `{issueKey, name, type}` index
> (32 KB is ~500 such entries), refreshed on write and rebuilt from search when stale.
> `searchJiraIssuesWithJQL` (`src/jira-oidc-helpers/jira.ts:126`) already builds arbitrary query
> params, so testing this is cheap. **Do it before writing any of this code.**

Either way this design is search-dependent, and the search endpoint has already moved once under us
(`spec/search-api-deprecation.md`). Route everything through the existing helpers rather than
issuing raw requests.

## Costs, honestly

- **Someone has to create the project.** That's a site-admin action in most orgs. Mitigate by letting
  the user _point at an existing project_ rather than requiring a new one — the app only needs a
  project key, and it can create its issues in someone's existing `OPS` project just as well.
- **Saving requires Jira write permission** in that project. Today saving requires nothing beyond app
  access. This is a genuine capability regression for read-only users, and it's the strongest
  argument for keeping app-property storage as a supported mode rather than a deprecated one.
- **Reports become issues**, which means they surface in boards, backlogs, velocity charts, dashboard
  gadgets, and global search. Recommend a **company-managed project with no board**, and document a
  `project != STATREPS` clause for customers' saved filters. Issue-created notifications should be
  suppressed via the project's notification scheme.
- **Two more round trips per save** (property + description) versus one today.
- **Orphaned issues.** Deleting a report should transition to Done, not hard-delete — recoverable,
  and it keeps the history that was half the point.
- **Report-of-reports references.** A `sections` tree stores `{reportId}`
  (`.../ReportOfReports/model/sections.ts`). Those ids must resolve after migration — see below.

## `TEAMMAP` specifically

Everything above applies, plus two team-specific notes:

**The TR-133 constraint is load-bearing.** The website backend mirrors team velocity/tracks/sprint
length into a human-readable table in the config issue's description
(`src/jira/storage/index.web.ts:128-155`) _because the Jira Auto Scheduler reads that table._ It is
marked temporary in the code, but something outside this repo depends on it. A `TEAMMAP` migration
must either keep writing that table for as long as the Auto Scheduler needs it, or be coordinated
with a matching change there. **This is the single biggest gotcha in the whole plan** — treat it as a
blocking dependency, not a cleanup task.

**`fixAnyNonExistingFields` gets cheaper.** Today, discovering that one team references a deleted Jira
field rewrites the entire `all-team-data` blob
(`.../team-configuration/fetcher.ts:48`). Per-team issues make that a per-team write.

**A team issue is a natural home for more than config.** Once a team is an issue you can hang the
team's owner, its Jira `Team` field value, its Confluence space link, and its members off it — which
is presumably why "team map" is the better name. Worth designing the payload with room for that, but
not worth building it now.

## Migration

The ids are the hard part. `Report.id` today is an arbitrary key in a JS object; after migration the
natural id is the Jira issue key. Report-of-reports documents reference reports by that id
(`{type: 'saved-report', params: {reportId}}`), so a naive re-keying breaks every composed document.

**Keep the old id.** Store it in the payload (`{legacyId, queryParams, sections}`) and keep resolving
by it. The issue key becomes the storage address; `legacyId` stays the application-level identity.
New reports can use the issue key as both. This is a few lines in the resolver and it makes migration
non-destructive.

Then:

1. **Point** — user picks or creates the project; the app writes the pointer (see
   [002](./002-pluggable-backends.md)).
2. **Copy forward** — read the blob, create one issue per record, preserving `legacyId`. Idempotent:
   re-running matches on `legacyId` and updates rather than duplicating.
3. **Dual-read, single-write** — reads prefer the project and fall back to the blob for anything
   missing; writes go to the project only. The blob becomes a frozen backup.
4. **Verify and cut over** — show the user a reconciliation ("42 reports migrated, 42 found") and let
   _them_ press the button that stops the fallback read.
5. **Retain** — leave the blob untouched for at least one release. It's ~32 KB. There is no reason to
   ever delete it automatically.

Throughout: keep writing the TR-133 team table.

## Alternatives considered

**Attachments on a single issue** — 1 GB per file, effectively unlimited count. Genuinely the most
storage available. Rejected: no partial read (every list downloads everything), no per-record
permissions, no history, and attachments are trivially deleted by any user with attachment-delete
permission. All the downsides of a blob plus a download.

**Project properties on an existing project** — 32 KB each, unlimited count, scoped to a project the
customer already has. This is a _real_ middle option: better than app properties (per-project scope,
so a permission story exists at the project level; unlimited count, so sharding is natural) and much
cheaper than one-issue-per-report (no project creation, no issue noise, no write permission needed
beyond project admin). It does not give per-report ACLs, history, or comments. **Worth prototyping as
the low-effort variant** if `STATREPS` proves too heavy for the median customer.

**Forge migration** — 240 KiB per key, 4,000 writes/min, and Atlassian is steering everyone there
anyway. Strictly better than Connect app properties on every axis. But it's a platform migration, not
a storage change, and 240 KiB is still a blob — it fixes the ceiling and none of the three structural
problems. Track it separately.
