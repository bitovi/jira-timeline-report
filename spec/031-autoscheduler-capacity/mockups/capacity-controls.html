Auto-Scheduler — editable capacity and tracks

Mockup for spec/031. The team header row becomes the place you change a plan's assumptions: click capacity to edit it, step the track count in place, and keep the change as a what-if until you commit it. Nothing here is live — it is static HTML showing the states.

The row splits on the one distinction that matters: everything you can change is on the left, packed against the team name; everything the model computes is on the right. Capacity is an input, so it moves left next to the track stepper. Points / Day is a unit conversion of capacity and Total Working Days is a result of the simulation, so both stay right, read-only.

3 — Uncommitted changes

A change takes effect in the plan immediately — that is the point of a what-if — but it does not touch your saved team settings until you commit it. One row-level treatment says so, and it is identical whether capacity or tracks moved. Reset and Commit act on inputs, so they join the left group.

The amber fill and left edge mark the row, not the field. That is what makes capacity and tracks behave alike — a dirty-input style would have worked for the one and had no equivalent for the other. The pair of buttons is the second half of the signal: they exist only while something is uncommitted, so their presence is itself the indicator. They appear at the end of the input group, so the row grows leftward and the outputs never move.

Control Does
Reset Drops this team's override. The row returns to saved settings and the plan re-solves.
Commit Writes capacity and tracks through to team settings — the same store Settings → Teams edits — and clears the row treatment. Affects every report.
Overrides are session state. They are not written to the URL and not carried by a saved report: a shared link that silently showed a plan built on capacity that does not exist would be a worse bug than losing an uncommitted what-if on reload.

Untouched teams look exactly as they do today — no amber, no buttons. Each team commits or resets on its own; a change to one team is not entangled with a change to another. Because the outputs are right-aligned, they line up into readable columns down the report whether or not a team has pending changes.

4 — Tracks

The stepper sits next to the team name, where the original tool's + was — and, under the new arrangement, at the head of the input group. The original put − on the Track 1 label row; putting both in one control means the count is readable at a glance, and it survives the case where a track has no work and its label row is not rendered.

ORDER 1 track
PLATFORM 7 tracks

− stops at 1, because a team with zero tracks cannot be scheduled. There is no upper bound — how many streams a team runs is not ours to cap.

Adding a track does not add capacity. totalPointsPerDay is unchanged by tracks; only pointsPerDayPerTrack moves. Two tracks means each epic takes twice as long and two run side by side. Tracks trade latency on one chain for parallelism across chains — they help a wide plan and do nothing for a single dependency chain.

The tooltips that have to say so

Tracks — 2 Parallel work streams inside this team. Each track works one epic at a time.
Adding a track does not add capacity. The team still delivers 2.1 points/day; each track now gets 1.05, so every epic takes about twice as long and two run at once.
Epics with no estimate also shrink — their default estimate is capacity ÷ tracks.
Points / Day — 2.1 Capacity ÷ sprint length = 21 ÷ 10 business days.
Change capacity to move this. It is a readout, not a setting.

5 — Rejected options

Option Why not
Everything right-aligned, as the row is today no Mixes the two numbers you set with the two the model computes, so nothing on the row tells you which is which. Inputs left, outputs right makes that readable without a single word of explanation.
A global “2 teams changed — Reset all / Save all” bar no A second place to commit, far from the thing being committed, and it forces an all-or-nothing decision across teams you changed for unrelated reasons. Per-team Reset / Commit says the same thing next to the change.
“was 21”, “(1.75 / track)”, before → after diffs on the row no Noise on a row that already carries four values plus three controls. The amber row says something changed; Reset puts it back. Nobody needs the old number quoted at them to use either.
A maximum track count no How many parallel streams a team runs is a fact about that team, not a limit for this tool to impose.
A bespoke edit affordance — pencil, dotted underline, bordered chip no Jira has one click-to-edit idiom and this app already uses it twice. Anything else makes capacity look like a different kind of control than every other editable value in the product.
Editable Points / Day no Arithmetically it back-solves to capacity = pointsPerDay × sprintLength, but two editable fields bound to one stored value means every edit silently rewrites the other, and rounding makes the round-trip lossy — type 2.13, get 21 pts/sprint, see 2.1. One input, one readout.
Editable Total Working Days no It is an output of the simulation. Back-solving capacity from it is not well defined.
Overrides in the URL / saved report no A shared link would silently show a plan built on capacity that does not exist.
