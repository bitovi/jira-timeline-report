## Question 3 answered: yes, read _and_ write

A Forge front end can read **and write** Connect app properties with **no backend and no resolver**,
provided the app declares the same `app.connect.key`.

Verified 2 Sep on `prodcheck` / `arthurpankiewicz.atlassian.net`, via `@forge/bridge`'s
`requestJira` against `/rest/atlassian-connect/1/addons/bitovi.status-report/properties/…`:

- `saved-reports`, `reports-storage-config`, `all-team-data`, `features`, `theme` — all `200` with
  real data (`reports-storage-config` = `{"kind":"legacy"}`)
- Write lifecycle on a throwaway key: `PUT 201` → `GET 200` (exact value) → `DELETE 204` → `GET 404`

Consequences:

1. **The cutover is seamless.** Customers keep the store they already have. No migration, no admin
   action, and the "empty app" support ticket predicted at [plan.md:165](./plan.md) is avoidable.
2. **No resolver.** [resolver-storage/plan.md](../resolver-storage/plan.md) is unblocked by not
   being needed.
3. **The "storage disagreement" risk is void.** [plan.md:102-104](./plan.md) warns a Forge `main`
   and a Connect `deeplink` could read different stores. They cannot — both reach the same app
   properties. Modules can be converted one at a time.

## The target shape, proven

`app.connect.key` is **separable** from "fully Forge". `forge eligibility` on a manifest with the
key, a remote, native Forge modules and no `connectModules` named only the _remote_ as
disqualifying — never the key. And the key with **no** `remotes` block lints clean.

Proven on `prodcheck` v5 (`Connect keys: 2`, `Remotes: 0`, native modules only):

- Connect app properties still read `200` with real data — access survives with no remote
- `forge eligibility` → _"eligible for the Runs on Atlassian program"_

Then with the real app deployed in that shape:

- `save` / `save2` — reports that site already had — **appear in a native Forge module**, with no
  migration and nothing configured
- Saving a new report persisted across a hard refresh — [plan.md](./plan.md)'s "Writes work" row,
  against the real bridge rather than a mock
- The Storage panel shows the **In Jira** card as live, Key/Value selected, matching the
  `{"kind":"legacy"}` pointer

**So: native Forge modules, no `connectModules`, no `remotes`, keep `app.connect.key`.**

### The `deeplink` task

The Connect module is a `generalPage` with `location: none` whose URL carries a hardcoded parameter
list that Jira substitutes (`scripts/atlassian-connect/index.ts`):

```
/connect.html?primaryIssueType={ac.bitovi.status-report.primaryIssueType}
              &jql={ac.bitovi.status-report.jql}
              &cardsMode={ac.bitovi.status-report.cardsMode}
              …9 params
```

The open question: **how does a Forge module receive equivalent parameters?** `{ac.*}` substitution
is a Connect descriptor feature with no direct Forge analogue. Candidates are the Forge context or
the URL mirror in `src/routing/index.forge.ts`. Read how the deeplink is _consumed_ before choosing —
[plan.md:49-51](./plan.md) notes that param list is frozen and coordinated with the published
descriptor.

Note the scope change on any Forge build: production declares 2 scopes, a Forge build needs
`read:jira-work` / `write:jira-work` too. That is a major version, so each site admin must approve
before the upgrade takes effect. Cloud Marketplace apps auto-update, so customers cannot stay on
1.20-AC — but the approval gate means the rollout is not instant.

## How to build, deploy and verify

**Node ≥ 22.12 is required** — the Forge CLI `require()`s ESM-only `archiver`, which fails on older
Node with `ERR_REQUIRE_ESM`. `.nvmrc` pins `v22.23.2`. `npm overrides` cannot fix it (`@forge/cli`
ships its own `npm-shrinkwrap.json`, which overrides cannot penetrate).

Build with the **production** Connect app key, or the adapter reads the wrong addon's properties:

```bash
nvm use
VITE_JIRA_APP_KEY=bitovi.status-report npm run build:forge
# sanity: the key should appear in dist-forge/assets/*.js, and bitovi.timeline-report.local should not
```

`forge deploy` needs the manifest and `dist-forge` in the same directory, and the repo's root
`manifest.yml` points at the sandbox — so deploy from a scratch directory holding this manifest plus
a copy of `dist-forge`:

```yaml
app:
  id: ari:cloud:ecosystem::app/12573c92-9009-45d3-ab51-46f65ffa1ba1
  runtime:
    name: nodejs22.x
  connect:
    key: bitovi.status-report # what grants access to existing customers' reports

modules:
  jira:globalPage:
    - key: status-reports-global
      resource: main
      title: Status Reports for Jira
      layout: blank
  jira:projectPage:
    - key: status-reports-project
      resource: main
      title: Status Reports for Jira
      layout: blank

resources:
  - key: main
    path: dist-forge

permissions:
  scopes:
    - read:jira-work
    - write:jira-work
    - read:connect-jira # reaches the Connect app properties
    - write:connect-jira
  content:
    styles:
      - unsafe-inline # Atlaskit is Emotion-based and injects styles at runtime
```

```bash
npx --prefix <repo> forge deploy -e prodcheck --approve MAJOR_VERSION_RULE
npx --prefix <repo> forge install --upgrade -e prodcheck
```

**Never `-e production` while testing** — the default environment is production, and a manifest
without `connectModules` deployed there would strip the Connect modules from every customer.
**If prompted to delete the Connect key, answer `N`** — that key is what grants access to customer
data.

Verify on `arthurpankiewicz.atlassian.net`: `save` / `save2` / `save3` listed, Storage panel showing
**In Jira** as the live card. Useful read-only commands: `forge version list -e <env>`,
`forge version details -e <env>`, `forge install list`, `forge eligibility -e <env>`.

## After the transition: move new installs to Forge KVS

**Not part of this release.** Do it once the fully-Forge version has shipped and settled.

Reading Connect app properties is a _compatibility_ mechanism, so existing customers keep their
reports without lifting a finger. It should not be the default for installs with no Connect history.

| Install                       | Store                                                                          |
| ----------------------------- | ------------------------------------------------------------------------------ |
| Existing customers, untouched | Connect app property (today's behaviour), or a Reports Space if they chose one |
| **New installs**              | **Forge KVS**                                                                  |

Most existing sites are expected to end up on a Reports Space anyway — host-neutral, no Connect key
needed — leaving Connect app properties as a shrinking legacy tail.

Depends on, in order:

1. **Ask Atlassian whether Connect app properties are supported past Connect end of support**
   (Dec 2026). Their docs endorse reading them from Forge but say nothing about deprecation. The
   answer sets the deadline. The Marketplace review on 2.0.0/2.1.0 is a live channel for asking.
2. **Forge KVS needs a resolver** — `@forge/kvs` is server-side, so this would be the app's first
   backend, plus a `storage:app` scope (a major version). Costed in
   [resolver-storage/plan.md](../resolver-storage/plan.md).

Dropping `app.connect.key` is the last step, and only once nothing still reads a Connect app
property — the key is what grants that access.

### No auto-migration to a Reports Space

Migrating `legacy` (Key/Value) → `space` **cannot** be automated: it needs a space that already
exists in the customer's instance and its key typed in, and it creates Jira work items in their
instance, which an app should not do unprompted. It stays an admin choice in the Storage panel.

Also: you cannot ask customers to migrate _before_ upgrading. Cloud apps auto-update, and the admin
who approves the permission prompt is rarely the person who knows about Reports Spaces — you would be
racing your own customers. The adapter removes the need entirely.

### Why the card says "In Jira"

The Storage panel's cards are split by store, and Forge shares Connect's. "Connect" names an
implementation detail a Jira admin cannot see or act on, and once `connectModules` are gone there is
no Connect app on the site for the word to refer to — while the reports stay where they are.
Labelling by _location_ outlives the platform name. The Connect dependency is documented in
`jira/storage/index.forge.ts` and here, deliberately **not** in the UI.

## Also worth fixing, unrelated to the code

The Marketplace security questionnaire attached to the pending versions answers "no" to using
`asUser()`, and states the app _"doesn't make any requests outside of Jira"_.

- The first **understates** the app's posture. It has no backend, so `@forge/api` is unreachable and
  it _cannot_ escalate — per Atlassian's docs, _"There is no equivalent of `asApp()` on the
  `@forge/bridge` package: calls from front-end code always run with the permissions of the current
  user."_ A bare "no" reads as "we skip user authorization"; the truth is the opposite.
- The second is **inaccurate** for v2, whose UI loads from `statusreports.bitovi.com` (`Remotes: 1`)
  and which ships Sentry with `tracesSampleRate: 1.0`. Note browser tracing captures URLs, and this
  app's URLs carry report state including **JQL** — worth checking what actually reaches Sentry
  before writing any privacy declaration.

Related trap for the CI work in [plan.md § Phase 7](./plan.md): `generate-build-env.sh` writes a
`.env` containing `VITE_FRONTEND_SENTRY_DSN`, and Vite reads `.env` automatically — so adding
`npm run build:forge` to `deploy-prod.yaml` would silently give the Forge bundle a live Sentry DSN,
adding egress, requiring an `egress` manifest block, and breaking Runs on Atlassian eligibility. Set
that variable empty explicitly on the Forge build step.
