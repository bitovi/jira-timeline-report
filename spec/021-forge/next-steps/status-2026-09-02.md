## Decisions now settled

## Question 3 answered: **yes, read _and_ write**

A Forge front end can read _and_ write Connect app properties with **no backend and no resolver**,
provided the app declares the same `app.connect.key`.

Verified 2 Sep on `prodcheck` / `arthurpankiewicz.atlassian.net`, from `@forge/bridge`'s
`requestJira` against `/rest/atlassian-connect/1/addons/bitovi.status-report/properties/…`:

- `saved-reports`, `reports-storage-config`, `all-team-data`, `features`, `theme` — all `200`
  with real data (`reports-storage-config` = `{"kind":"legacy"}`)
- Write lifecycle on a throwaway key: `PUT 201` → `GET 200` (exact value) → `DELETE 204` → `GET 404`

Consequences:

1. **The cutover can be seamless.** Customers keep reading and writing the store they already have.
   No migration, no admin action, and the "empty app" support ticket predicted at
   [plan.md:165](./plan.md) is avoidable.
2. **No resolver.** [resolver-storage/plan.md](../resolver-storage/plan.md) was blocked on this
   answer; it is not needed for the cutover.
3. **The "storage disagreement" risk is void.** [plan.md:102-104](./plan.md) warns that a Forge
   `main` and a Connect `deeplink` could read from different places. They cannot — both reach the
   same app properties. Modules can therefore be converted one at a time.

The only app **without** a Legacy badge is the fully-Forge sandbox. The hybrid — Forge modules _and_

## `app.connect.key` is separable from "fully Forge"

`forge eligibility` on a manifest with the Connect key, a remote, a native Forge module and **no**
`connectModules` reports only:

- App is using remote services
- App is egressing data

Both are the remote. The Connect key is **not** a disqualifier, and a manifest declaring
`app.connect.key` with no `remotes` block passes `forge lint` cleanly.

So the target shape is: **native Forge modules, no `connectModules`, no `remotes`, keep
`app.connect.key`** — fully Forge, Runs-on-Atlassian-eligible, and still able to reach every
customer's existing saved reports.

**Proven end to end on 2 Sep.** `prodcheck` v5 (`Connect keys: 2`, `Remotes: 0`, modules
`jira:globalPage: 1` only):

- Connect app properties still read `200` with real data — access survives with no remote
- `forge eligibility` → _"eligible for the Runs on Atlassian program"_

This is the shape the fully-Forge release should take.

## No auto-migration to a Reports Space

Migrating `legacy` (Key/Value) → `space` cannot be automated: it requires a space that already
exists in the customer's instance and its key typed in. It also creates Jira work items in a
customer's instance, which an app should not do unprompted. It stays an admin choice in the Storage
panel, and is **not** coupled to this release.

The Connect-app-property dependency still wants resolving before Connect's end of support, but on
its own timeline.

## The cutover is proven end to end

The real app, built fully Forge (`app.connect.key` retained, no `connectModules`, no `remotes`) and
deployed to `prodcheck` on `arthurpankiewicz.atlassian.net`:

- The saved reports that site already had (`save`, `save2`) **appear in a native Forge module** — no
  migration, nothing configured, no admin action
- The Storage panel shows the **Connect** card as the live one, Key/Value selected, matching the
  `{"kind":"legacy"}` pointer
- Saving works: a new report survived navigating away and a hard refresh — [plan.md](./plan.md)'s
  "Writes work" verification row, against the real bridge rather than a mock

The Storage panel's first card is titled **"In Jira"**, not "Connect". The cards are split by store,
and Forge shares Connect's — but "Connect" names an implementation detail a Jira admin cannot see or
act on, and once `connectModules` are gone there is no Connect app on the site for the word to refer
to. Labelling by _location_ outlives the platform name. The Connect dependency is documented in
`jira/storage/index.forge.ts` and here, which is where the people who can act on it will look; it is
deliberately **not** surfaced in the UI.

## After the transition: move new installs to Forge KVS

**Not part of this release. Do it once the fully-Forge version has shipped and settled.**

Reading Connect app properties is a _compatibility_ mechanism: it exists so existing customers keep
their reports without lifting a finger. It should not be the default for installs that have no
Connect history.

The end state worth aiming at:

| Install                       | Store                                                                          |
| ----------------------------- | ------------------------------------------------------------------------------ |
| Existing customers, untouched | Connect app property (today's behaviour), or a Reports Space if they chose one |
| **New installs**              | **Forge KVS**                                                                  |

Most existing sites are expected to end up on a Reports Space anyway, which is host-neutral and needs
no Connect key. That leaves Connect app properties as a shrinking legacy tail rather than the path
every new customer lands on.

Two things this depends on, in order:

1. **Ask Atlassian whether Connect app properties are supported past Connect end of support**
   (Dec 2026). Their docs endorse reading them from Forge but say nothing about the deprecation. The
   answer sets the deadline for everything above. The Marketplace review on 2.0.0/2.1.0 is a live
   channel for asking.
2. **Forge KVS needs a resolver** — `@forge/kvs` is server-side, so this is the first thing that
   would give the app a backend, plus a `storage:app` scope (a major version). Costed in
   [resolver-storage/plan.md](../resolver-storage/plan.md), which today is unblocked-by-not-being-needed
   rather than resolved.

Dropping `app.connect.key` is the last step, and only once no install still reads a Connect app
property — the key is what grants that access.

So an existing customer upgrading from Connect keeps their reports, silently. This is the behaviour
the release depends on, and it is no longer inferred.

Implemented in `src/jira/storage/index.forge.ts` (`createForgeConnectStorage`), wired at
`src/forge.main.ts`. `Storage.tsx` now splits its two cards by _store_ rather than host —
`host !== 'hosted'` — because Forge shares Connect's.
