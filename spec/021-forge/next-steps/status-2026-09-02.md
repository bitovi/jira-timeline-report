## Decisions settled

**Convert the existing app, not a new listing.** [plan.md § The one decision that gates
everything](./plan.md#the-one-decision-that-gates-everything) treats this as open. It isn't — Phase A
shipped 19 Aug against the existing app key. **Phase A (Step 2) is done.**

**`deeplink` is dropped, not ported.** Nothing in this repo has ever generated a URL to it
(`git log -S deeplink` across all history finds only the descriptor generator), it is not documented
on the public Confluence space, and it is not needed to remove the last Connect module. Forge also
has no equivalent of `location: none` on a global page, so porting it would have added a second
"Status Reports for Jira (Deep Link)" entry to every customer's Apps menu. Arthur's call, 2 Sep:
not mission critical to going fully Forge; add it back later if anyone misses it.

**Module keys are `main` and `project`, matching the old Connect keys.** This is the one piece of
backward compatibility that cannot be retrofitted — see [Forge URL persistence](#forge-url-persistence-replaces-acsubstitution).

**All four scopes are required — do not trim them.** `read:jira-work` / `write:jira-work` are not
optional extras on top of `read:connect-jira` / `write:connect-jira`. Proven on prodcheck 2 Sep by
deploying without them and watching Jira REST fail while the app still rendered. The Connect
compatibility scopes reach Connect's own endpoints, not the Jira REST API. Full evidence in
[release-runbook.md § Step 3](./release-runbook.md) and in `manifest.yml`'s own comment.

**Admin approval on upgrade is acceptable.** Arthur's call, 2 Sep. That closes the question of
whether `read:jira-work` / `write:jira-work` count as scopes _inherited_ from Connect's coarse
`read` / `write` (no approval, developer bulk-upgrade) or as _additional Forge-specific_ scopes
(per-site admin approval). Plan for the latter; if it turns out to be the former, the rollout is
simply faster than expected. Detail in [ci-cd.md](./ci-cd.md).

**Sentry is off on Forge by construction, not by environment.** `forge.main.ts` passes
`FRONTEND_SENTRY_DSN: ''` as a literal. It previously read
`import.meta.env.VITE_FRONTEND_SENTRY_DSN`, which left the guarantee resting on the ambient
environment: `scripts/generate-build-env.sh` writes a `.env` containing that variable and Vite loads
`.env` automatically, so one run of that script would have given the Forge bundle a live DSN with
nothing failing. With `tracesSampleRate: 1.0` and report state (including JQL) in the URL, that
would mean customer JQL leaving Jira. The website and Connect builds still read it from the
environment.

## Question 3 answered: yes, read _and_ write

A Forge front end can read **and write** Connect app properties with **no backend and no resolver**,
provided the app declares the same `app.connect.key`.

Verified 2 Sep on `prodcheck` / `arthurpankiewicz.atlassian.net`, via `@forge/bridge`'s
`requestJira` against `/rest/atlassian-connect/1/addons/bitovi.status-report/properties/…`:

- `saved-reports`, `reports-storage-config`, `all-team-data`, `features`, `theme` — all `200` with
  real data (`reports-storage-config` = `{"kind":"legacy"}`)
- Write lifecycle on a throwaway key: `PUT 201` → `GET 200` (exact value) → `DELETE 204` → `GET 404`

Consequences:

1. **The cutover is seamless.** Customers keep the store they already have. No migration, no admin
   action, and the "empty app" support ticket predicted at [plan.md:165](./plan.md) is avoidable.
2. **No resolver.** [resolver-storage/plan.md](../resolver-storage/plan.md) is unblocked by not
   being needed.
3. **The "storage disagreement" risk is void.** [plan.md:102-104](./plan.md) warns a Forge `main`
   and a Connect `deeplink` could read different stores. They cannot — both reach the same app
   properties. Modules can be converted one at a time.

### Forge URL persistence replaces `{ac.*}` substitution

The question this section used to pose — _how does a Forge module receive equivalent parameters?_ —
has an answer, and it is neither the Forge context nor a hand-rolled scheme.
[Redirecting URLs from Connect to Forge](https://developer.atlassian.com/platform/adopting-forge-from-connect/migrate-page-module-urls/):

> Forge performs matching via module ID: `{addonKey}__{moduleKey}`. Jira/Confluence finds the Forge
> app whose `app.connect.key` in the manifest file matches the Connect app key, then finds the Forge
> module whose key matches the obsolete Connect module key.

Jira then redirects, base64-encoding the **entire** original Connect URL — path, query string and
fragment — into an `x_atlassian_cf` param on the Forge URL, read through the bridge:

```js
const { location } = await view.createHistory();
const original = atob(new URLSearchParams(location.search).get('x_atlassian_cf'));
```

Three consequences:

1. **It lands in `forgeHistory.location.search`** — the exact value `reconcileRoutingState` already
   reads at `src/routing/index.forge.ts:38`. The hook point exists; nothing decodes it yet.
2. **The frozen nine-param list dies.** The whole original query string survives, so a forwarded URL
   can carry any param — `tableColumns`, `filterRows`, `report` — not just the nine
   [plan.md:49-51](./plan.md) describes as coordinated with the published descriptor.
3. **Module keys must match, which is why they are `main` and `project`.** The earlier
   `status-reports-global` / `status-reports-project` would have broken URL persistence for _all_
   modules, not just `deeplink` — including every customer bookmark of
   `/plugins/servlet/ac/bitovi.status-report/main`, which is simply what the address bar shows when
   you open the app today.

**Not built:** the `x_atlassian_cf` decoder. Without it a forwarded bookmark lands on the app
unconfigured rather than restoring its report state. A pure function plus one wiring line in
`reconcileRoutingState`; deferred deliberately, and the natural home for `deeplink` support if it is
ever wanted back.

**Verified 2 Sep on prodcheck: Forge deep links already work.** Configuring a report, copying the
browser URL and opening it cold in a new tab brings the same report back. So an inbound container URL
carrying app params does reach `forgeHistory.location.search`, and `reconcileRoutingState`
(`src/routing/index.forge.ts:38`) replays it before `route.start()`. The
[Verification](../plan.md#verification) table's "URL state" row passes.

**This is what makes dropping `deeplink` safe rather than merely expedient.** Sharing a configured
report is what that module existed for, and on Forge the app's own URL does it — with every param,
not the nine the Connect descriptor froze. The `x_atlassian_cf` decoder remains unbuilt and is now
narrowly scoped: it would only matter for an _old Connect bookmark_ restoring its state, and such a
bookmark already lands on the working app.

### Rollout

**The scopes are not what makes this a major version.** Tested 2 Sep: `forge lint` reports the
identical `MAJOR_VERSION_RULE` — _"Change due to **migration key modification**"_ — both with four
scopes and with only the two (`read:connect-jira` / `write:connect-jira`) that production v2 already
declares. The trigger is the Connect migration key changing, not the permission set.

**Resolved 3 Sep — `Connect keys: 2` is one key registered for two products, not two keys.**
`forge version details -e production` (needs a TTY; pick "Show all properties") reports:

```
connect keys   - [jira]:       bitovi.status-report
               - [confluence]: bitovi.status-report
```

The **key value is unchanged** in the new manifest, which matters: Atlassian states
`app.connect.key` _"cannot be mutated (added, removed or changed) in any further production
deployments"_ ([How to adopt Forge from Connect](https://developer.atlassian.com/platform/adopting-forge-from-connect/how-to-adopt/)).
We declare the same string, so nothing protected is being changed.

What _is_ changing is the rest of the Connect block. Production pairs the key with a remote:

```
remotes        - [connect]: baseUrl: https://statusreports.bitovi.com
                            operations: - storage
```

The new manifest drops `app.connect.remote` and the `remotes` block entirely — deliberately, since a
remote is what disqualifies Runs on Atlassian. That removal is the "migration key modification". It
is already proven harmless: prodcheck runs with `Remotes: 0` and still reads Connect app properties,
and the full verification pass on 3 Sep found saved reports, writes and the Reports Space all
working. Note the remote's `operations: [storage]` in particular — despite the name, removing it does
not cost access to the app properties where saved reports live.

Two residual unknowns, neither blocking:

- The single unqualified `key:` may register for Jira only, where production registered both
  products. The app has no Confluence modules, so nothing of ours depends on the Confluence side —
  but **if the Marketplace listing claims Confluence support, that is a listing question worth
  checking** before the production deploy.
- The "cannot be mutated" wording is about _production_ deployments. The prodcheck deploy succeeded,
  which is good evidence but not proof for production. If `forge deploy -e production` rejects the
  Connect block, that is why.

That reframed the scope question: trimming scopes cannot buy a minor version locally, so the only
thing it could affect is the Marketplace-side classification and the permission prompt customers see.

**Tested on prodcheck, 2 Sep — the answer is no.** Deployed with only `read:connect-jira` /
`write:connect-jira` (the two scopes production v2 declares), the app installed and rendered, but:

- reading a Reports Space failed with _"Could not read \"REPTEST\". Check the space key and that you
  have access to it."_ — `react/services/reports-storage/useSpaceIssueTypes.ts:62`, wrapping
  `fetchProjectIssueTypes`, a plain Jira project read
- saved reports did not load

So the legacy Connect compatibility scopes cover the Connect endpoints, not the Jira REST API that
`requestJira` calls. Atlassian's
[scope equivalences page](https://developer.atlassian.com/platform/adopting-forge-from-connect/connect-to-oauth2-scope-equivalences/)
does not state this either way; it was settled empirically. `read:jira-work` / `write:jira-work` are
restored, and **this release does genuinely increase the declared scope set** — so plan on the
customer permission prompt, which was already accepted.
That is accepted — see [Decisions settled](#decisions-settled). Atlassian classifies Connect→Forge
changes on a [separate table](https://developer.atlassian.com/platform/adopting-forge-from-connect/connect-forge-updates/)
that may be more permissive; [ci-cd.md](./ci-cd.md) has the detail.

**Confirmed 2 Sep: no customer is on the Forge `production` environment.** Customers are on the
Connect version `1.2.0-AC`; 2.0.0 and 2.1.0 are Connect-on-Forge, pending approval, never released.
`forge install list` shows only `bitovi-training` (development) and `arthurpankiewicz` (prodcheck).
So deploying the fully-Forge manifest to `production` strips Connect modules from an environment
nobody is running — the warning elsewhere in this document applies to the _default_ environment
being production, not to a live customer base.

The plan is to put the fully-Forge version up for approval **behind** the pending 2.x versions and
flag to the reviewer that it is the one customers should land on, so they skip Connect-on-Forge
entirely. Open question for that reviewer: what happens if 2.0.0/2.1.0 are approved _after_ the
fully-Forge version.

**The Marketplace version number is not ours to pick.** Atlassian detects the production deploy and
publishes a version within minutes, bumping **major** when scopes increase or change and **minor**
otherwise ([Upgrade and version cloud apps](https://developer.atlassian.com/platform/marketplace/upgrading-and-versioning-cloud-apps/)).
Removing the Connect modules alone would be a minor bump — `2.2.0`. What should make it major is the
two added scopes (`read:jira-work` / `write:jira-work` on top of the two `*:connect-jira` ones),
giving `3.0.0`. If Atlassian instead treats those as _inherited_ from Connect's coarse `read` /
`write`, it lands as `2.2.0`. Do not plan around either number until the console shows it.

Note this is a different counter from Forge's own major-version integer, which `forge version list`
reports as `2` in production and which this deploy takes to `3`.

## How to build, deploy and verify

**Node ≥ 22.12 is required** — the Forge CLI `require()`s ESM-only `archiver`, which fails on older
Node with `ERR_REQUIRE_ESM`. `.nvmrc` pins `v22.23.2`. `npm overrides` cannot fix it (`@forge/cli`
ships its own `npm-shrinkwrap.json`, which overrides cannot penetrate).

Build with the **production** Connect app key, or the adapter reads the wrong addon's properties:

```bash
nvm use
VITE_JIRA_APP_KEY=bitovi.status-report npm run build:forge
# sanity: the key should appear in dist-forge/assets/*.js, and bitovi.timeline-report.local should not
```

`forge deploy` needs the manifest and `dist-forge` in the same directory, and the repo's root
`manifest.yml` points at the sandbox — so deploy from a scratch directory holding this manifest plus
a copy of `dist-forge`:

```yaml
app:
  id: ari:cloud:ecosystem::app/12573c92-9009-45d3-ab51-46f65ffa1ba1
  runtime:
    name: nodejs22.x
  licensing:
    enabled: true # REQUIRED — this is a paid app. See the warning below.
  connect:
    key: bitovi.status-report # what grants access to existing customers' reports

modules:
  jira:globalPage:
    - key: status-reports-global
      resource: main
      title: Status Reports for Jira
      layout: blank
  jira:projectPage:
    - key: status-reports-project
      resource: main
      title: Status Reports for Jira
      layout: blank

resources:
  - key: main
    path: dist-forge

permissions:
  scopes:
    - read:jira-work
    - write:jira-work
    - read:connect-jira # reaches the Connect app properties
    - write:connect-jira
  content:
    styles:
      - unsafe-inline # Atlaskit is Emotion-based and injects styles at runtime
```

> **`licensing.enabled: true` is load-bearing and was missing from this block until 3 Sep.**
> Deploying without it shipped production major version 3 with `License: false` (v2 had `true`) —
> visible in the `License` column of `forge version list -e production`. Nothing errors: with no
> license on the view context, `getLicensing()` in `src/forge.main.ts:28` takes its deliberate
> "absent means allowed" branch and every install runs fully functional and unlicensed. On a paid
> app that is revenue exposure, and paid→free is a licensing change Atlassian classifies as major.
> Fixed in major version 4. **Always check the `License` column after a production deploy.**

```bash
npx --prefix <repo> forge deploy -e prodcheck --approve MAJOR_VERSION_RULE
npx --prefix <repo> forge install --upgrade -e prodcheck
```

**Never `-e production` while testing** — the default environment is production, and a manifest
without `connectModules` deployed there would strip the Connect modules from every customer.
**If prompted to delete the Connect key, answer `N`** — that key is what grants access to customer
data.

Verify on `arthurpankiewicz.atlassian.net`: `save` / `save2` / `save3` listed, Storage panel showing
**In Jira** as the live card. Useful read-only commands: `forge version list -e <env>`,
`forge version details -e <env>`, `forge install list`, `forge eligibility -e <env>`.

## After the transition: move new installs to Forge KVS

**Not part of this release.** Do it once the fully-Forge version has shipped and settled.

Reading Connect app properties is a _compatibility_ mechanism, so existing customers keep their
reports without lifting a finger. It should not be the default for installs with no Connect history.

| Install                       | Store                                                                          |
| ----------------------------- | ------------------------------------------------------------------------------ |
| Existing customers, untouched | Connect app property (today's behaviour), or a Reports Space if they chose one |
| **New installs**              | **Forge KVS**                                                                  |

Most existing sites are expected to end up on a Reports Space anyway — host-neutral, no Connect key
needed — leaving Connect app properties as a shrinking legacy tail.

Depends on, in order:

1. **Ask Atlassian whether Connect app properties are supported past Connect end of support**
   (Dec 2026). Their docs endorse reading them from Forge but say nothing about deprecation. The
   answer sets the deadline. The Marketplace review on 2.0.0/2.1.0 is a live channel for asking.
2. **Forge KVS needs a resolver** — `@forge/kvs` is server-side, so this would be the app's first
   backend, plus a `storage:app` scope (a major version). Costed in
   [resolver-storage/plan.md](../resolver-storage/plan.md).

Dropping `app.connect.key` is the last step, and only once nothing still reads a Connect app
property — the key is what grants that access.

### No auto-migration to a Reports Space

Migrating `legacy` (Key/Value) → `space` **cannot** be automated: it needs a space that already
exists in the customer's instance and its key typed in, and it creates Jira work items in their
instance, which an app should not do unprompted. It stays an admin choice in the Storage panel.

Also: you cannot ask customers to migrate _before_ upgrading. Cloud apps auto-update, and the admin
who approves the permission prompt is rarely the person who knows about Reports Spaces — you would be
racing your own customers. The adapter removes the need entirely.

### Why the card says "In Jira"

The Storage panel's cards are split by store, and Forge shares Connect's. "Connect" names an
implementation detail a Jira admin cannot see or act on, and once `connectModules` are gone there is
no Connect app on the site for the word to refer to — while the reports stay where they are.
Labelling by _location_ outlives the platform name. The Connect dependency is documented in
`jira/storage/index.forge.ts` and here, deliberately **not** in the UI.

## Also worth fixing, unrelated to the code

The Marketplace security questionnaire attached to the pending versions answers "no" to using
`asUser()`, and states the app _"doesn't make any requests outside of Jira"_.

- The first **understates** the app's posture. It has no backend, so `@forge/api` is unreachable and
  it _cannot_ escalate — per Atlassian's docs, _"There is no equivalent of `asApp()` on the
  `@forge/bridge` package: calls from front-end code always run with the permissions of the current
  user."_ A bare "no" reads as "we skip user authorization"; the truth is the opposite.
- The second is **inaccurate** for v2, whose UI loads from `statusreports.bitovi.com` (`Remotes: 1`)
  and which ships Sentry with `tracesSampleRate: 1.0`. Note browser tracing captures URLs, and this
  app's URLs carry report state including **JQL** — worth checking what actually reaches Sentry
  before writing any privacy declaration.

Related trap for the CI work in [plan.md § Phase 7](./plan.md): `generate-build-env.sh` writes a
`.env` containing `VITE_FRONTEND_SENTRY_DSN`, and Vite reads `.env` automatically — so adding
`npm run build:forge` to `deploy-prod.yaml` would silently give the Forge bundle a live Sentry DSN,
adding egress, requiring an `egress` manifest block, and breaking Runs on Atlassian eligibility. Set
that variable empty explicitly on the Forge build step.
