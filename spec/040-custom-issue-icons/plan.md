# Review: custom issue-type icon plan vs. docs + this repo

## Context

Custom Jira issue-type icons don't render in the Forge app. A pasted plan proposes proxying icons through a Forge resolver as `data:` URLs. This file records what holds up against Atlassian docs/community reports, what doesn't fit this repo, and the revised approach.

## Verdict on the plan's claims

| Claim                                                                                                                                       | Status                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| ------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Custom-type `iconUrl` from Forge is `api.atlassian.com/ex/jira/{cloudId}/rest/api/2/universal_avatar/...` and a plain `<img>` can't load it | **Holds up, but the cause is wrong.** The gateway URL needs a bearer token and `<img>` sends none, so it returns 401/403. CORS isn't involved for `<img>`. Tracked as ECO-56.                                                                                                                                                                                                                                                                                                                               |
| CORS breaks `mask-image`                                                                                                                    | True (CSS masks are fetched in CORS mode), **but doesn't apply here.** This repo has no `mask-image`. Icons are plain `<img>` in `EstimationProgress.tsx:346`, `PercentCompleteModal.tsx:78`, `EstimateBreakdownModal.tsx:191`, `TableReport/model/fieldTypeRegistry.ts:252`.                                                                                                                                                                                                                               |
| Strip everything before `/rest/` before `requestJira`                                                                                       | **Holds up.** A community fix reports the same thing.                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| `read:avatar:jira` is required                                                                                                              | **Wrong per Jira's OpenAPI spec** (swagger-v3.v3.json, all three `universal_avatar/view/*` GETs). The classic scope `read:jira-work` is listed as `state: Current` and `read:avatar:jira` as the `Beta` granular alternative, so either should satisfy it. We already declare `read:jira-work`. Endpoint permission: none for system avatars; _Browse projects_ for custom issue-type avatars. Still confirm on prodcheck, because the other project reported a non-OK response without the granular scope. |
| `external.images` is only needed for direct `<img>`                                                                                         | Partly. Reports put the default `img-src` at `'self' data: blob: … https://api.atlassian.com`, so `data:`/`blob:` are already allowed and `*.atlassian.net` isn't. Built-in icons served from the site domain may still be blocked by CSP. Reports also say a `*.atlassian.net` entry is unreliable.                                                                                                                                                                                                        |
| `/images/icons/issuetypes/epic.svg` can be fetched through `requestJira`                                                                    | **Unproven.** It isn't a REST path and the gateway may not proxy it. The unit test only checks the string rewrite, not that the fetch works.                                                                                                                                                                                                                                                                                                                                                                |
| Code paths `app/src/backend/*`, `app/manifest.yml`                                                                                          | **Don't exist here.** The plan was written for another codebase.                                                                                                                                                                                                                                                                                                                                                                                                                                            |

## Conflicts with this repo

1. **Architecture:** `manifest.yml:32-38` and `:64-68` state the resolver only touches KVS, and that every Jira call goes through `@forge/bridge` `requestJira` in the iframe. That keeps calls off the invocation quota. A resolver-side `api.asUser().requestJira` breaks that rule.
2. **Major version:** Adding a scope or changing CSP (`external.images`) is a major version, and admins have to re-consent. If either is needed, bundle it into the pending spec/041 major (`read:jira-user`).

## Recommended approach (frontend, no resolver)

- Add a small helper next to `src/request-helpers/forge-request-helper.ts`. It strips the icon URL to its `/rest/…` path, calls the bridge `requestJira`, then `res.blob()` → `URL.createObjectURL` (`blob:` is already in the default `img-src`). Memoize per URL so each icon is fetched once per session.
- Use it only for the Forge build and only for `universal_avatar` URLs. Leave web/Connect `<img src>` untouched. Fall back to the raw URL or nothing on failure.
- Route the four `<img>` call sites through one `IssueTypeIcon` component or hook.
- **Spike first:** confirm the bridge `requestJira` returns intact binary for PNG custom avatars. Its docs only promise "a WHATWG Response" and say nothing about binary. If it comes back corrupted, fall back to the resolver + base64 approach from the pasted plan and update the manifest comments.
- Scope: no change expected, since `read:jira-work` covers `universal_avatar` per the OpenAPI spec. Add `read:avatar:jira` only if prodcheck returns 401/403 anyway. With the `blob:` approach the CSP doesn't change either, so this can ship as a **minor** version.

## Verification

- Deploy to prodcheck (user runs the forge commands). Use a site with one custom-icon issue type and one built-in type. Check that the icons render in the Gantt percent-complete modal, the table Issue Type column, and estimation progress. Check the network tab for 200 responses and the console for no CSP violations.
- Add unit tests for the URL→path stripping and the memoized fetch (mock `@forge/bridge`).

## Status (2026-10-14)

Implemented, not yet verified on prodcheck.

- `src/shared/jira-image-src.ts`: host-injected resolver (same pattern as `reload-app.ts`); the default is identity.
- `src/request-helpers/forge-image-loader.ts`: Forge resolver. Converts `universal_avatar` URLs to a `/rest/…` path, fetches through bridge `requestJira`, then `blob()` → `createObjectURL`. Memoized; falls back to the raw URL on failure. Installed in `forge.main.ts`.
- `src/react/components/JiraImage`: `<JiraImage>` / `useJiraImageSrc`, used at all five issue-type icon sites (the four above plus `normalizedRenderers.tsx` `iconRender`).
- Binary spike: `@forge/bridge` 6.2.0's `productFetchApi` already decodes `isAttachment` responses from base64 to a `Blob` (`out/fetch/fetch.js`). Whether the host flags image responses that way is only provable on prodcheck.
